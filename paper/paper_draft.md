# SleepSpot：基于 vLLM Sleep Mode 的 Spot 实例大模型推理快速恢复方案

> 论文初稿 v0.3（润色版）· 2026-10-15
> 实验环境：NVIDIA RTX 4090 24GB · vLLM 0.8.5 (V1 Engine) · Qwen2.5-1.5B/7B-Instruct

---

## 摘要

大语言模型（LLM）推理服务正加速向云原生架构演进，抢占式实例（Spot Instance）以远低于按需实例的价格成为降低推理成本的关键手段。然而 Spot 实例随时可能被回收，推理服务在实例重建时需经历完整的冷启动——模型权重重新加载进 GPU 显存——导致服务恢复时间高达数十秒，严重制约了低成本推理的可用性。

本文提出 SleepSpot，一种将 vLLM Sleep Mode 与 Spot 实例回收通知机制相结合的推理快速恢复方案。其核心思想是：在收到回收信号时，推理引擎主动通过 Sleep Mode 将 GPU 显存中的模型权重与 KV Cache 释放（权重保留于主机内存），进程与运行时状态得以存活；当回收窗口过去或请求再次到达时，仅需通过内存重映射即可在亚秒级完成恢复，跳过完整的权重加载过程。

我们在 RTX 4090 上基于 vLLM 0.8.5，以 Qwen2.5-1.5B（3.1 GB 权重）和 Qwen2.5-7B（15 GB 权重）为负载完成对照实验：1.5B 冷启动平均 **49.73 秒**，Sleep L1 唤醒（含首次推理）约 **0.25 秒**，加速约 **200 倍**；7B 冷启动平均 **54.09 秒**（首次含一次性初始化 78.69 秒），L1 唤醒端到端约 **0.85 秒**，加速约 **64–93 倍**。进入睡眠仅需 1.0–1.5 秒，可释放约 **95%** 的 GPU 显存。我们在两种规模上均复现了 vLLM 0.8.5 V1 引擎 Sleep Level 2 未真正丢弃主机侧权重副本的版本局限，并总结出三项工程落地经验。本方案在长驻推理实例场景下验证，其核心机制对 Serverless 推理平台的冷启动优化具有参考价值。

**关键词**：云原生推理；Spot 实例；大模型推理；冷启动；vLLM；Sleep Mode

## 1 引言

### 1.1 背景

LLM 推理服务具有显著的潮汐特征：请求量随时间剧烈波动，夜间低谷期的算力若按峰值预留将造成大量浪费。云原生架构通过弹性扩缩容、按量计费天然契合这一负载模型。与此同时，云厂商提供的抢占式实例（Spot/AWS、抢占式/阿里云等）价格仅为按需实例的 20%–40%，但随时可能被回收，通常仅提前 30–60 秒通知。

二者结合是降低推理成本的自然方向，但面临一个核心恢复难题：

1. **冷启动（Cold Start）**：实例从零拉起时，模型权重需从磁盘加载进 GPU 显存。实测显示，1.5B 模型在 RTX 4090 上约需 50 秒，7B 模型约需 54–79 秒（取决于 OS page cache 与初始化状态）；
2. **Spot 回收（Preemption）**：实例被回收后，即使快速在别的机器上重新拉起，同样要经历完整的冷启动。

现有工作 SpotServe [1] 通过参数并行重映射实现 stateful 恢复，但需要对推理框架做深度定制，难以直接落地于以 vLLM 为代表的主流推理引擎生态。Serverless 推理平台（如 ServerlessLLM [2]）通过多级缓存与快照加载缓解冷启动，但仍需在实例重建时完成权重的加载或恢复。

### 1.2 我们的观察与方案

2025 年 3 月发布的 vLLM Sleep Mode 提供了一个此前不存在的原语：推理引擎可以在**不销毁进程**的前提下主动释放 GPU 显存（权重下放主机内存），并在需要时通过**内存重映射**快速恢复。这启发了 SleepSpot 的核心思路：

> **把"Spot 回收后的恢复"从"进程级冷启动"降级为"进程内的睡眠唤醒"。**

具体地：推理服务收到 Spot 回收通知（或空闲检测触发）后调用 Sleep API 释放显存，进程本身保持存活；GPU 显存被释放的部分可让渡给同机其他任务（如另一副本或作业），提高整机利用率；当回收窗口过去（Spot 容量恢复）或系统决定复用该实例时，Wake API 在亚秒级恢复服务，完全跳过权重加载阶段。

### 1.3 贡献

- 提出并实现 SleepSpot 方案，将 vLLM Sleep Mode 嵌入 Spot 回收-恢复生命周期，无需修改推理框架内核；
- 在真实 GPU 环境（RTX 4090 + vLLM 0.8.5 V1）上完成了 1.5B 与 7B 两个模型规模、冷启动/Sleep L1/Sleep L2 三种场景 × 3 次重复的对照实验，量化恢复加速比与显存释放率；
- 在两种模型规模上均复现并验证了 vLLM 0.8.5 V1 引擎 Level 2 睡眠未真正丢弃权重副本的版本局限；
- 分析了 Sleep Mode 对 Serverless 推理平台冷启动优化的参考价值与适用边界。

## 2 背景与相关工作

### 2.1 LLM 推理的冷启动

冷启动耗时由三部分构成：进程与 CUDA 上下文初始化、模型权重从磁盘加载至显存、KV Cache 等运行时结构分配。权重加载占主导——以 BF16 存储的 1.5B 模型约 3.1 GB，7B 模型约 15 GB，在机械盘或低带宽实例上动辄数十秒。ServerlessLLM [2] 采用多级缓存与快照加载缓解该问题，但依赖定制的存储与调度栈。

### 2.2 vLLM 与 Sleep Mode

vLLM [3] 凭借 PagedAttention 成为当前最广泛使用的开源推理引擎。Sleep Mode（v0.7.3 引入）提供两个 REST 端点：

- `POST /sleep?level=1|2`：释放 GPU 显存。Level 1 将权重保留在主机内存；Level 2 额外丢弃主机副本（设计语义）；
- `POST /wake_up`：恢复显存映射并恢复服务，支持按 tag 选择性唤醒（`weights` / `kv_cache`）。

其底层依赖 CUDA 虚拟内存 API（cuMemCreate/cuMemMap）：权重缓冲区按物理页管理，睡眠时解除 GPU 侧物理页映射并保留主机侧数据，唤醒时重新映射，无需重新反序列化权重文件。

### 2.3 Spot 实例与容错推理

Spot 回收应对策略可分为三类：(a) **checkpoint-restore**（如 SpotServe [1] 在实例间重分布参数分片）；(b) **无状态重建**（主流 Serverless 平台的默认行为，等价于冷启动）；(c) **主动休眠**——即本方案路线：在回收前将服务置入低资源状态，回收窗口内进程不死亡或以最小状态存活，回收结束后原地快速恢复。与 (a) 相比，本方案无需修改推理框架；与 (b) 相比，恢复时间从分钟级降至亚秒级。据我们调研，在 vLLM Sleep Mode（2025 年 3 月发布）之上构建 Spot 弹性推理的公开工作尚不多见，本方案属于对新原语的组合式应用。

## 3 SleepSpot 设计

### 3.1 生命周期

SleepSpot 将推理实例的生存周期扩展为五个状态（如图 1 所示）：

```
                    ┌──────────────────────────────────────┐
                    │                                      │
  ┌────────┐ spawn  ▼        ┌────────┐   sleep    ┌──────────────┐
  │ 冷启动 │──────▶ Serving ◀───wake───│  Sleeping  │── 触发条件 ──│
  └────────┘           │        └────────┘            └──────────────┘
                       │                                  ▲
                       │ spot 回收通知                     │
                       ▼                                  │
                 ┌───────────┐      sleep(1.0~1.5s)        │
                 │ Finalizing│──────────────────────────────┘
                 └───────────┘
```

**图 1**　SleepSpot 推理实例五态生命周期

- **Serving → Sleeping**：控制器收到 Spot 回收通知（或平台空闲策略触发），调用 `POST /sleep?level=1`；
- **Sleeping 状态**：进程存活、权重在主机内存、GPU 显存释放约 95%，可被让渡；
- **Sleeping → Serving**：Spot 容量恢复或新请求到达时调用 `POST /wake_up`；
- **Finalizing**：若回收最终发生，进程正常退出；在新实例上按冷启动路径重建（本文将其作为对照基线）。

### 3.2 关键设计决策

1. **选择 Level 1 而非 Level 2**：L1 将权重保留于主机内存，唤醒仅需重映射；L2 丢弃主机副本、唤醒需重读磁盘，适用于主机内存紧张的场合（见第 5.4 节的版本局限分析）。
2. **睡眠窗口与请求排空**：sleep 调用必须在无在途请求时进行（实测在途请求会导致引擎崩溃，见 5.5 节），控制器先停止接流、等待排空（亚秒级）再触发睡眠。
3. **唤醒时机**：收到平台"回收撤销/容量恢复"信号立即唤醒（最优路径）；未收到信号但负载预测显示请求将到时，提前唤醒以覆盖尾部延迟。

## 4 实验设置

| 项 | 配置 |
|---|---|
| GPU | NVIDIA RTX 4090 24 GB（单卡） |
| 引擎 | vLLM 0.8.5（V1 Engine，`--enable-sleep-mode`，`--gpu-memory-utilization 0.85`，`--max-model-len 512`） |
| 模型 | Qwen2.5-1.5B-Instruct（BF16，权重约 3.1 GB）；Qwen2.5-7B-Instruct（BF16，权重约 15 GB） |
| 计时方式 | 进程内计时 + `nvidia-smi` 显存采样 + 服务端日志交叉验证 |

**场景与重复次数**（每种场景 3 次重复）：

- **冷启动**：完全终止进程 → 等待显存归零 → 重新 `vllm serve` → 记录从启动到 `/health` 就绪（ready_time）及首次推理完成（total_to_infer）；
- **Sleep L1 wake**：就绪并预热后 `POST /sleep?level=1` → `POST /wake_up` → 记录 wake API 耗时、显存恢复耗时、恢复后首次推理；
- **Sleep L2 wake**：同上，level=2。

每次冷启动前均确认 GPU 显存回落至 2 MiB，排除前序实验干扰；L1/L2 试验在同一进程内交替进行。

## 5 实验结果

### 5.1 主结果：恢复时间（1.5B）

**表 1**　1.5B 模型冷启动 vs. Sleep 唤醒对比

| 场景 | 就绪/恢复耗时 (s) | 含首次推理 (s) | 相对冷启动加速 |
|---|---|---|---|
| 冷启动 trial 1（真冷，磁盘读） | 51.40 | 51.74 | 1x |
| 冷启动 trial 2（OS page cache 热） | 48.37 | 48.66 | 1x |
| 冷启动 trial 3 | 49.42 | 49.72 | 1x |
| **冷启动均值** | **49.73 ± 1.25** | **50.04 ± 1.27** | — |
| Sleep L1 wake × 3（wake API） | 0.15 / 0.15 / 0.15 | 端到端 ≈ 0.25 | **≈ 200x** |
| Sleep L2 wake × 3 | 0.02 / 0.02 / 0.02 | 端到端 ≈ 0.12 | 见 5.4 节 |

### 5.2 主结果：恢复时间（7B）

**表 2**　7B 模型冷启动 vs. Sleep 唤醒对比

| 场景 | 就绪/恢复耗时 (s) | 含首次推理 (s) | 相对加速 |
|---|---|---|---|
| 冷启动 trial 1（含一次性初始化：JIT 编译等） | 78.69 | 79.11 | — |
| 冷启动 trial 2（稳态） | 53.42 | 53.82 | 1x |
| 冷启动 trial 3（稳态） | 54.43 | 54.90 | 1x |
| **冷启动均值（稳态）** | **54.09** | **54.53** | — |
| Sleep L1 wake × 3（wake API） | 0.71 / 0.64 / 0.64 | 端到端 ≈ 0.85 | **≈ 64x（稳态）/ ≈ 93x（首次）** |
| Sleep L2 wake × 3 | 0.02 / 0.02 / 0.03 | 端到端 ≈ 0.18 | 见 5.4 节 |

要点：

1. **恢复时间从约 50–79 秒降至亚秒级**。1.5B 的 L1 唤醒稳定在 0.15 秒；7B 的 L1 唤醒为 0.64–0.71 秒（15 GB 权重重映射），端到端含首次推理约 0.85 秒。相比同规模稳态冷启动（54.53s）加速约 **64 倍**；相比含一次性初始化开销的首次冷启动（78.69s，对应真实 Spot 新实例拉起场景）加速约 **93 倍**；
2. **冷启动时间的构成分析**：7B 与 1.5B 的稳态冷启动仅差约 4 秒（54.09 vs 49.73），说明 vLLM 启动瓶颈主要是固定开销（CUDA 上下文、引擎初始化、图编译等约 45–50 秒），而非权重加载（safetensors 的 mmap 加载在现代 NVMe 上吞吐很高）；7B 首次启动比稳态慢约 24.6 秒，主要是一次性初始化（flashinfer JIT 编译 CUDA 内核）与 page cache 填充——Sleep 方案将这两类开销全部跳过；
3. **睡眠成本可忽略**：进入睡眠耗时 1.0–1.5 秒（1.5B）/ 0.6–1.4 秒（7B，首次 9.44s 含一次性初始化），且仅在回收前执行一次；
4. **显存释放彻底**：1.5B 睡眠后显存从 21 012 MiB 降至 980 MiB（释放 95.3%）；7B 睡眠后从约 20 GiB 降至 1 058 MiB（释放约 95%）。

### 5.3 Mac 原型交叉验证

在 Apple M4（统一内存）上以轻量负载模拟"冷启动 vs 睡眠唤醒"的早期原型给出同方向结论：Naive 重载 6.07s，L1 恢复 1.36s（**4.5x**），L2 恢复 1.49s（**4.1x**）。倍率低于 GPU 平台，原因是原型中冷启动基数较小（6 秒 vs 50 秒），符合"模型越大、Sleep 唤醒收益越大"的预期。

### 5.4 发现：vLLM 0.8.5 V1 的 Level 2 未真正丢弃主机副本

按设计语义，L2 应丢弃主机侧权重副本，唤醒时需从磁盘重载，耗时应在秒级。然而实测结果与预期不符：1.5B 的 L2 唤醒仅 **0.009–0.02 秒**，7B 的 L2 唤醒仅 **0.02–0.03 秒**，均快于各自 L1 唤醒（0.15 s / 0.64–0.71 s），与"从磁盘重载"的物理约束矛盾。三组旁证进一步支持这一判断：

- **主机内存对照**：1.5B 实验中 L1 与 L2 睡眠期间 RAM 占用几乎不变（约 2.2 GB），说明 L2 并未释放权重副本；
- **显存一致性**：7B 实验中 L1 与 L2 睡眠后 GPU 显存完全相同（均为 1058 MiB），若 L2 丢弃了副本应有差异；
- **服务端日志**：无权重重载相关记录。

我们据此判定：**该版本 V1 引擎的 L2 行为与 L1 等价，权重副本未被真正丢弃**（社区存在同类 issue），且该现象在 1.5B 与 7B 两种规模上稳定复现。本文将 L1 作为主结果，对 L2 完整语义的验证留作未来工作。

### 5.5 工程经验

Sleep Mode 从论文特性到真实落地，我们遇到并解决了三个非显而易见的问题，为后续研究者提供参考：

1. **路由开关**：vLLM 0.8.5 的 `/sleep`、`/wake_up` 端点被 `VLLM_SERVER_DEV_MODE=1` 环境变量门控，缺省返回 404，文档未显式说明；
2. **子进程清理**：V1 引擎的 EngineCore 子进程由 multiprocessing spawn 而来，命令行不含 "vllm" 字样，`pkill -f vllm` 无法命中，会遗留占用约 20 GB 显存的孤儿进程——必须按 `nvidia-smi --query-compute-apps` 返回的 PID 精确清理；
3. **JIT 依赖**：flashinfer 首次启动需 JIT 编译 CUDA 内核，依赖 `ninja`；以绝对路径裸启动服务时 PATH 不含 conda 环境 bin 目录，会以 `Ninja is required` 失败。此外，**必须确保 sleep 时无在途请求**，否则引擎将以 CUDA 非法访问崩溃（EngineDeadError）。

## 6 讨论

**适用边界**：Sleep 唤醒的收益由两部分被跳过的开销决定——引擎固定初始化（约 45–50 秒，与模型规模无关）和权重加载（随规模线性增长，7B 约 15 GB）。本文在 1.5B 与 7B 上的实测表明：即便在 NVMe 高速存储上，两个规模的唤醒端到端均在亚秒级（0.25s / 0.85s），相对稳态冷启动加速 200 倍与 64 倍；在更大模型（13B+）或低速存储（网络盘）场景，权重加载占比上升，加速比将进一步扩大。同时，Sleeping 状态要求主机内存 ≥ 权重大小（L1），内存紧张的小规格实例可权衡 L2（待引擎修复其语义）。

**与 SpotServe 的关系**：SpotServe 解决的是"实例死了之后跨机恢复"，需要参数级重分布；SleepSpot 解决的是"实例还活着时的最低资源维持"，二者互补——完整的 Spot 推理系统可在回收窗口内先尝试进程内唤醒（本文路径），失败后再走跨机重建（SpotServe 路径）。

**对 Serverless 推理平台的参考价值**：本文方案在长驻推理实例场景下验证，并非面向"实例即销毁"的纯 FaaS 模式。其参考价值体现在三方面：(1) **原语有效性验证**——Sleep Mode 将权重加载这一冷启动核心步骤从数十秒压至亚秒级，为 Serverless 平台的冷启动优化提供了可借鉴的技术路径；(2) **工程边界暴露**——无在途请求才能 sleep、子进程清理、JIT 依赖等条件，是 Serverless 平台集成该原语时必须前置处理的约束；(3) **收益天花板量化**——在 NVMe 单卡上 200x/64x 的加速表明该方向值得投入，且在网络盘等低速存储场景收益将更大。若 Serverless 平台未来支持"实例休眠态保留"（类 AWS EC2 Hibernate），本方案的机制可直接迁移。

**局限性**：(1) 单卡实验，尚未覆盖多卡张量并行与 13B 以上更大模型；(2) 7B 冷启动的稳态样本受益于 OS page cache（模型文件已驻留内存），但真实 Spot 同机快速重启场景同样受益于该缓存，且我们同时报告了含一次性初始化的首次启动数据（78.69s），故不影响结论方向；(3) 唤醒延迟测量含本机 HTTP 往返，跨节点调用会引入额外网络开销（毫秒级，不改变量级结论）。

## 7 结论与未来工作

本文提出了 SleepSpot——将 vLLM Sleep Mode 与 Spot 实例回收生命周期相结合的 LLM 推理快速恢复方案，并在真实 GPU 环境上针对 1.5B 与 7B 两个模型规模完成了量化验证。实验表明：

- **恢复时间从分钟级降至亚秒级**：50–79 秒 → 0.25–0.85 秒，加速 200 倍 / 64 倍（相对含初始化首次冷启动达 93 倍）；
- **资源让渡彻底**：睡眠转换成本约 1.5 秒，GPU 显存释放率约 95%；
- **工程可落地**：无需修改推理框架内核，仅依赖 vLLM 标准 API。

未来工作：(1) 扩展至 13B+ 模型与多卡张量并行场景，验证唤醒时间的规模效应；(2) 构建基于负载预测的自动睡眠/唤醒控制器，量化"误唤醒"与"唤醒滞后"的成本权衡；(3) 在真实 Spot 回收-恢复事件流（而非模拟信号）上做端到端可用性评估；(4) 跟进 vLLM 新版本对 L2 语义的修复并重新评估两级睡眠的适用边界。
